# I1（P0）：隔离端到端基线

## 目标

让一次端到端分数严格表示“指定数据场景在指定 LightRAG 环境中的表现”。每次运行
必须经历数据集入库、处理完成校验、索引快照、检索和回答评测，不能复用未知的
全局知识库。

## 用户故事

- 作为实验用户，我希望选中一个生成数据集后，系统测到的就是这批数据，而不是
  API 中以前残留的文档。
- 作为模型选型者，我希望更换模型或 Embedding 后，平台自动采用正确的重建范围。
- 作为维护者，我希望外接模型凭据集中在服务端配置档案中，而不是由前端传递。

## 功能需求

### FR-1.1 环境配置档案

- 新增 `EnvironmentProfile`，由服务端管理，包含：
  - LightRAG 版本/镜像或启动模板；
  - 抽取/KG、查询、回答、Embedding、VLM、Reranker 的 provider 与模型引用；
  - 解析引擎、存储后端、默认检索与并发配置；
  - 密钥引用（secret reference），不保存和返回明文。
- Profile 分为草稿和已发布版本；run 只能引用已发布版本和不可变版本号。
- 任何变更产生新版本，不修改被历史 run 引用的版本。

### FR-1.2 隔离工作空间与生命周期

- 一个端到端 run 使用唯一的 `workspace_id` 和 `storage_id`；两者与 run 一一对应。
- 平台可按已发布的环境档案启动或分配被测 LightRAG 执行单元；执行单元必须能返回
  实际配置快照。
- 已完成/取消/失败后的工作空间保留策略可配置：保留用于诊断、定期归档或安全清理；
  清理不得影响其他 run。
- 不允许在共享全局 workspace 上执行标记为端到端的 run。

### FR-1.3 受控入库与入库回执

- 数据集文件按 manifest 逐个上传；每个文件记录上传 ID、内容 hash、处理状态、
  解析时间、失败原因。
- 只有全部必需文件达到终态且成功率满足计划阈值时，才能进入检索/回答阶段。
- 系统必须记录索引回执：成功/失败文档数、chunk 数、实体数、关系数、向量集合/工作
  空间标识、索引完成时间。
- 发生部分失败时默认停止并标记 `ingestion_failed`；用户可在计划中明确允许“按成功
  文件继续”，报告必须显示样本污染风险。

### FR-1.4 端到端基线协议

- 新建 `end_to_end_baseline` 替代当前仅调用查询 API 的在线基线。
- 固定阶段：环境预检 → 隔离实例准备 → 上传 → 等待处理 → 入库校验 → 检索评测 →
  回答评测 → 归档。
- `online_baseline` 保留为 legacy/高级工具，其报告必须注明“未验证数据集入库，不可
  作为端到端配置比较”。
- 所有阶段将 workspace、输入哈希和 runtime snapshot 写入 I0 的 manifest。

### FR-1.5 幂等、取消与恢复

- run 在上传阶段可安全恢复，已确认相同 hash 的文件不得重复入库。
- 取消必须停止后续阶段，并保留已完成阶段及其回执。
- 服务重启后可据持久化状态恢复展示和安全清理；不得将不完整 workspace 误标为完成。

## API 与数据变更

- 新增/演进：`/eval/environment-profiles`、`/eval/runs/{id}/ingestion`、
  `/eval/runs/{id}/workspace`。
- `EvaluationPlan` 至少引用 `dataset_version`、`environment_profile_version`、
  `experiment_type`、保留策略与入库成功阈值。
- 运行产物新增 `ingestion_receipt.json` 和 `index_receipt.json`。

## 非目标

- 本迭代不实现模型排行榜和统计显著性。
- 本迭代不要求支持用户上传私有文档；数据源仍是现有生成数据集。
- 本迭代不以提升 LightRAG 算法分数为目标，只保证测量对象正确。

## 验收标准

- 端到端 run 的全部被测文件都有入库回执，且 workspace 与其他 run 不共享。
- 在全局 API 预先插入无关文件后，端到端 run 的结果不受其影响。
- 人为使一份文件解析失败时，默认不会生成“完整端到端得分”。
- 同一数据集、同一环境档案的重跑可通过 manifest 复现相同输入与实际配置。
